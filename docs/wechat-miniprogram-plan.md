# 原生微信小程序实施规划

日期：2026-11-07。工作分支：`feat/wechat-miniprogram`。

## 目标与当前基础

发布使用原生 WXML、WXSS、TypeScript 的微信小程序。先验证少量内置菜谱，再切换为菜谱 API 和外部图片，最终通过体验版、审核、正式发布。

当前仓库的 Web 阅览器是 React + Vite，不能直接作为原生小程序上传。可以复用菜谱解析规则、类型、分类、原料与步骤关联算法；页面、路由、存储、分享和计时器生命周期需要适配。

本地现有生成产物包含 373 道菜谱、10 个分类；`recipes.json` 为 1,247,347 字节，图片目录约 106 MB。这是当前产物的测量值，不保证与所有源文件完全一致。Web 当前全量加载 JSON，并在构建时复制图片，因此不能照搬打包方式。

## 技术与目录

- `miniprogram/`：原生小程序项目，包含首页/分类、搜索、详情、烹饪模式、收藏页面。
- `packages/recipe-core/`：从现有代码抽出的跨端类型、数据规范及纯函数，不依赖 DOM、React 或微信 API。
- `scripts/recipes/`：逐步抽取现有 `web/scripts/build-data.mjs`，统一输出 Web 数据、小程序样本、API 数据和图片清单；保留 Web 原有构建入口。
- `api/`：只读菜谱 API；上线平台在确认域名和国内访问质量后确定。

前端只调用 `RecipeRepository`：`listCategories()`、`listRecipes({ category, q, cursor, limit })`、`getRecipe(id)`。提供 `local` 和 `remote` 两种实现，页面不直接引用样本 JSON、不自行拼接请求 URL。开发构建选择数据源；正式构建只包含 remote 所需代码和明确指定的备用内容。

## 阶段一：少量内置内容验证

1. 建立原生项目、类型检查和开发者工具导入配置。
2. 通过明确的 ID 白名单生成 15–20 道样本，覆盖主要分类、有图/无图、长步骤、计时信息和中文路径。
3. 完成分类列表、搜索、详情、分步烹饪、本地收藏和单菜谱分享路径。首版蓝图改为纵向步骤与关联原料展示，交互式节点画布延后。
4. 样本默认只内置文本。确有离线验证需要时，仅附带 3–5 张压缩封面；其他图片使用外部 URL，尚无图片服务时显示占位图。
5. 不打包仓库菜谱目录、全量图片、Web 字体、Web 产物或缓存。通过独立小程序项目根目录和构建白名单控制上传范围。

验收：开发者工具及 iOS/Android 真机完成查找菜谱 → 查看原料 → 逐步烹饪 → 收藏 → 分享回流；断网仍可查看内置文本；无图有正常占位；主包以小于 1.5 MB 为内部预算，上传前以开发者工具包分析为准。该预算是工程目标，不是对平台当前限制的声明。

计时器存储目标结束时间和步骤 ID，切后台后按时间戳恢复；不承诺后台持续计时回调或后台到点通知。

## 阶段二：API 与图片服务

数据流：Markdown 与原图 → 解析/校验 → 版本化菜谱产物 + 图片清单 → 发布内容与图片 → API 查询 → 小程序。

### 只读 API v1

| 接口 | 用途 |
| --- | --- |
| `GET /v1/manifest` | schemaVersion、contentVersion、更新时间 |
| `GET /v1/categories` | 分类及数量 |
| `GET /v1/recipes?category=&q=&cursor=&limit=20` | 分页摘要，仅返回 id、名称、分类、难度、简介和封面 |
| `GET /v1/recipe?id=<URL编码后的完整ID>` | 单菜谱详情，避免现有含斜杠 ID 的路由歧义 |

沿用现有菜谱 ID，保证收藏和分享稳定；后续若改 ID，需要映射与重定向策略。详情保留原料、份量、步骤、火候、时间与提示，增加结构化步骤图片字段，避免小程序运行时解析 Markdown 图片语法。原料与步骤关联来自现有启发式解析，不把识别结果当作精确营养或操作判断。

API 返回统一成功/错误结构、内容版本、404 和限流状态；分页限制上限；支持 ETag/缓存与超时重试。内容量在当前规模下可由构建产物和只读索引服务，不必先建立数据库或管理后台。发布产物准备完整后再切换活动版本，保留上一版以便回滚。

### 图片

- 图片由对象存储加 CDN 提供 HTTPS URL，API 返回绝对 URL；不在客户端直接依赖 GitHub/LFS 下载地址。
- 封面缩略图和详情图分别生成，内容哈希进入路径；建议初始目标为缩略图 30–80 KB、详情图 100–250 KB，按实拍画质与真机兼容性调整。
- 列表只加载缩略图，详情懒加载；失败展示占位并允许重试。保留原图用于后续重新生成。
- 图片清单涵盖封面、正文、步骤 notes、tips 等所有引用，并校验真实文件存在；LFS 指针不能当图片上传。迁移既有内嵌 Markdown 图片引用，防止残留相对地址。
- 图片先上传验证，再发布引用这些图片的新内容；旧图保留一个回滚周期。

### 客户端缓存与切换

列表和详情按内容版本及 ID 缓存，设定容量与淘汰规则；先读缓存再刷新。首次请求失败提供重试，有缓存时标注离线状态。服务端 404 需明确提示内容已移除，不能悄悄显示另一道样本菜。收藏存 ID 与轻量快照，处理菜谱更新或下架。

验收：remote 构建不包含全量 JSON 和菜谱图片；列表分页、远程搜索、详情、收藏、分享可用；请求失败、图片失败、首次离线、缓存离线均有明确表现；内容更新无需重新打包客户端。

## 阶段三：发布准备与上线

1. 确定小程序主体、AppID、管理员和类目；核对届时要求的备案、内容说明与隐私披露。
2. 确定自有 API/图片域名和托管方式，优先考虑国内真机访问质量。现有 Cloudflare Worker 可用于原型评估，不直接假设其默认域名能满足正式发布要求。
3. 配置 HTTPS、证书和微信后台相关合法域名；使用 `wx.downloadFile` 保存分享图片时同时检查对应下载域名。最终域名要求按公众平台和官方文档逐项核实。
4. 第一版不引入登录、支付、评论、用户上传或云端收藏，减少服务端状态与发布依赖。收藏仅本地保存；如增加收集数据的能力，再同步调整隐私声明。
5. 分享直接进入指定详情页，支持中文及多层路径 ID；分享封面必须可公网访问。公开菜谱 API 不需要把 AppSecret 或任何管理密钥交给客户端。
6. 微信开发者工具上传开发版 → 真机检查 → 体验版验收 → 提交审核 → 审核通过后发布；保留客户端和内容版本回滚方案。

验收时关闭“忽略合法域名”等开发豁免；测试首次启动、弱网、真机图片、前后台切换、收藏持久化与分享回流。检查请求错误、图片 404 和 API 可用性，不在日志记录无关个人数据。

## 建议迭代顺序

| 里程碑 | 交付物 | 依赖 |
| --- | --- | --- |
| M1 原生原型 | 独立项目、15–20 道样本、列表/详情/搜索 | 可先使用测试配置；真机预览需适用 AppID |
| M2 使用闭环 | 烹饪模式、收藏、计时恢复、分享、包体报告 | 真机验证环境 |
| M3 内容外置 | 版本化导出、只读 API、图片存储/CDN、remote 模式 | 域名与托管选择 |
| M4 发布候选版 | 体验版、正式域名配置、弱网/兼容性验证 | AppID、主体与备案等平台要求 |
| M5 正式发布 | 审核通过、线上验证、回滚准备 | 微信审核结果 |

下一步从 M1 开始，先做样本数据访问层和原生列表/详情，之后补使用闭环。域名与主体准备可同步进行，不阻挡本地原型。
